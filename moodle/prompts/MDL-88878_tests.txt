Issue MDL-88878: aiprovider_openai: json_encode() escapes slashes in model name, causing 404 with OpenAI-compatible providers

When using {{aiprovider_openai}} with an OpenAI-compatible provider and a model name containing a forward slash (e.g. {{cortecs/Llama-3.3-70B-Instruct-FP8-Dynamic}}), all AI requests fail with HTTP 404.

*Root cause:*

In {{process_generate_text.php}} and {{process_generate_image.php}}, the request body is encoded as:

{noformat}body: json_encode($requestobj),{noformat}

PHP's {{json_encode()}} escapes forward slashes by default ({{/}} → {{\/}}), producing:

{noformat}{"model":"cortecs\/Llama-3.3-70B-Instruct-FP8-Dynamic",...}{noformat}

Some OpenAI-compatible providers cannot route the request when the model name contains escaped slashes and return HTTP 404 with empty body. This also triggers a secondary PHP {{TypeError}} in {{handle_api_error()}} because {{$bodyobj->error->message}} becomes {{null}}.

Although MOODLE_405_STABLE and MOODLE_500_STABLE are security-only, I'd like to request that this fix be included there as well.

Without {{JSON_UNESCAPED_SLASHES}}, PHP's {{json_encode()}} escapes forward slashes in URLs (e.g. {{https://api.openai.com}} becomes {{https:\/\/api.openai.com}}). This results in malformed JSON being sent to the OpenAI API, causing *all AI-assisted features to fail completely* for users on these versions. This constitutes a severe operational failure — the entire AI subsystem (text generation, image generation) stops working.

*Fix:*

{noformat}body: json_encode($requestobj, JSON_UNESCAPED_SLASHES),{noformat}

{{JSON_UNESCAPED_SLASHES}} is safe — it only affects the {{/}} character, which does not require escaping per RFC 7159. This is standard practice in all major OpenAI SDKs (Python, Node.js).
