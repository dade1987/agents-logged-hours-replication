Issue MDEV-41617: Index corruption on UPDATE of table with long unique hash collision and indexed virtual blob

h3. Reproduce

set debug_dbug= 'd,same_long_unique_hash';
insert t1 (id, a) values (1, 'a1'), (2, 'b1');
update t1 set a= 'a2' where id = 1;

h3. Expected
{code:sql}
check table t1 extended;
Table	Op	Msg_type	Msg_text
test.t1	check	status	OK
select * from t1 force index (v) order by v;
id	a	v
1	a2	v-a2

The old key of row 1 in index {{v}} is read from freed memory (0x8F8F8F8F is the debug fill of freed memory), so InnoDB does not find the record to update. {{v}} of the old row must stay {{'v-a1'}} until the update is done.

h3. Notes

{{handler::check_duplicate_long_entry_key()}} reads all rows with the same long unique hash. Each read ({{ha_index_read_map()}}, then every {{ha_index_next_same()}} hit) runs {{TABLE::update_virtual_fields(VCOL_UPDATE_FOR_READ)}}, which swaps {{Field_blob::value}} and {{read_value}} of virtual blob columns. The function swaps them back only once, after the first read. After an odd number of further hits, {{value}} holds the buffer of the row read by {{UPDATE}}, which {{record[1]}} points to, and {{TABLE::restore_blob_values()}} frees it. {{ha_update_row()}} then builds the old secondary index key from freed memory.

The {{same_long_unique_hash}} debug keyword gives all rows the same hash. Without it, the bug needs a real hash collision between rows with different values.

The code comes from MDEV-32012 (382c543f531). The fix is to swap back after each read, i.e. move the swap loop into the {{do ... while (ha_index_next_same())}} body.
